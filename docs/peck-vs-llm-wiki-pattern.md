# Peck vs. the LLM-wiki pattern

*Analysis for [kip-app#106](https://github.com/JWE24-code/kip-app/issues/106) — comparing Kip's Hatch / Peck / Groom against the "LLM wiki pattern" that the vault CLAUDE.md describes. Written 2026-09-02 against kip `scripts/` and kip-app at `c9ccac213` (v0.4.4).*

## 1. Introduction

#106 asks how Peck's retrieval loop — its skills, bounded skill loop, trace and telemetry — stacks up against the LLM-wiki pattern the author's Obsidian "second brain" vault runs: `1.Raw` → `2.Wiki` → `3.Templates` → `4.Output`, with Ingest / Query / Lint operations, where the wiki layer is a Claude-owned synthesis layer whose pages must stay traceable to raw items.

The one-paragraph verdict: **Kip already implements the pattern's query and audit layers well; its write layer and answer persistence are where it genuinely does not measure up.** Answer-level provenance is enforced end to end (prompt mandate → post-hoc verification → clickable citations → groom re-audit), retrieval really does read an index before any raw file is opened, and the append-only nest plus `clucks/` audit trail is *stricter* than what the pattern asks of its Claude-owned layer. What is missing is structural, not behavioural: nest pages carry no source back-link (while the eggs they came from already emit provenance frontmatter), the default hatch path drafts update bodies without ever reading the page it appends to, the per-page LLM summary index is populated at ingest and discarded before the answer prompt, and `fileAnswerToNest` — a complete, tested write path for persisting an answer — is unreachable from the app, so an answered question leaves no durable record of any kind. After adversarial verification, 27 of 28 findings survived; they deduplicate into seven filed backlog items (#112–#118).

## 3. The vault pattern, quoted

From #106 (summarising the vault CLAUDE.md):

> - Layer `1.Raw`: immutable source documents (inbox), never edited after capture.
> - Layer `2.Wiki`: Claude-owned synthesis layer. Every wiki page must be traceable to raw items (a `## Source` back-link line). Pages carry YAML frontmatter. Queries read the wiki **index** first, before touching raw items. **Synthesis is preferred over restatement**: a good wiki page compares/contrasts across multiple raw items rather than paraphrasing one file.
> - Layer `3.Templates`: page templates.
> - Layer `4.Output`: deliverables produced from the wiki, each with a `Reference.md` source-trace table and a `Tasks.md` checklist.
> - Operations: **Ingest** (raw → wiki), **Query** (index first, then raw), **Lint** (periodic checks: contradictions, orphan pages, un-ingested raw items).
>
> The wiki layer is owned/maintained by Claude; the human owns Raw and Output.

### Scope mapping

| Vault | Kip counterpart | Fit |
|---|---|---|
| `1.Raw` — immutable sources | `eggs/`, plus the other source roots `['eggs','journals','pages','whiteboards']` (`kip/scripts/lib/hatch.js:27`) | Convention only: immutability is documented (`kip/docs/GETTING-STARTED.md:93`, `:236`) and backed by a content-hash *re-derivation trigger*, not a guard (`hatched_sources` sha1, `kip/scripts/lib/roost.js:275-285`). Office conversion writes derived `.md` siblings *into* `eggs/` (`kip/scripts/lib/office.js:268-277`); skills are unsandboxed Node. |
| `2.Wiki` — Claude-owned synthesis | `nest/` (`entity` / `concept` / `source` pages) | Append-only (no code path deletes or rewrites nest prose — stricter than the vault asks), but **no `## Source` back-link** (`kip/scripts/lib/pages.js:56` writes only `{type, created, updated, tags}`), and the human co-edits it, because nest pages are ordinary Logseq pages in the open graph. |
| `3.Templates` | **— no counterpart** | Kip's page types are a discriminator (folder + validation), not a template layer. Nothing in the pattern's template sense is missing from Kip's goals; noted for completeness. |
| `4.Output` — deliverables with `Reference.md` trace | `exports/` (docx/pptx skills), chat answers, reminder prep briefs | `exports/` sits **outside the wiki loop entirely** — it is not in `SOURCE_ROOTS`, so a deliverable can never be hatched back, and no artifact records which question/pages produced it. |
| **Ingest** | **Hatch** — and also Peck's statement branch | Peck is not only Query: a told fact files unconditionally through `captureFacts` → `fileCapturedFacts` (`kip/scripts/lib/peck.js:403-411`). The vault Ingest's *reconcile-at-write* obligation lands on no Kip stage (§11). |
| **Query** | Peck's question branch | Index-first in the mechanical sense — FTS over `meta.db` runs before any nest file is opened (`kip/scripts/lib/peck.js:399-400`) — but it reads raw bodies, not a synthesis index. |
| **Lint** | Groom — and Hatch's pending list | Groom covers contradictions + orphans verbatim; the vault's third named check, *un-ingested raw*, is **not** groom's — it lives in hatch's `collectPendingSources` (`kip/scripts/lib/hatch.js:318-385`); groom reads only `pages` + `pages_fts` (`kip/scripts/groom.js:297-299`). |

The pattern has **4 layers and 3 operations; Kip has 3 layers and 3 verbs, with two operations spanning two verbs each**. That scattering is not pedantry — it is why the pattern's two obligations that require a *writer* (traceability-at-ingest, reconcile-at-write) fall through.

## 4. The Peck loop, as #106 frames it

#106 names the loop's artifacts explicitly; for completeness, what each actually is:

- **Skills** — built-ins under `kip/scripts/skills/*` (web-search, xlsx-csv, docx, pptx, reminders, kip-control), merged with user skills from `<coop>/.henhouse/skills/*` (user wins on name); a user skill that was never approved in `skills.json` is silently excluded (`kip/scripts/lib/skills.js:111-113`, `:204-225`).
- **The "≤4-iteration" skill loop** — a text-protocol ReAct loop: the model replies with `<use_skill name="X">{json}</use_skill>` or prose; `MAX_SKILL_ITERATIONS = 4` (`kip/scripts/lib/prompts.js:143`) bounds *skill executions*, while the loop itself runs `turn <= 4` (`:199`) — so up to **five** model turns inside the loop (a malformed call consumes a turn without executing anything, `:231-241`), then a forced final answer under the plain answer prompt (`:220-229`). Worst case for one question ≈ 5 loop calls + forced final + the conditional `extractKeyTerms` call + an optional web-fallback answer. The issue's "≤4 iterations" is off by one against the call budget, not the skill budget — relevant to kip-app#103 (loop-limit slider).
- **`peck-trace.jsonl`** — full prompt/response text, strictly opt-in: `--trace` on the CLI, or `KIP_PECK_TRACE=1` in the environment (`kip/scripts/chat.js:43` — reachable from the app only via inherited env). The app's own toggle passes literal `false` (`kip-app/src/main/frontend/components/chat.cljs:120`).
- **Per-phase telemetry** — content-free by construction: timing/count entries surfaced live via `<coop>/.roost/peck-progress.json`; `peck-metrics.json` likewise carries no content.
- **The ⚙ steps widget** — each step is `{skill, input, ok, ms, outputPreview}` (`kip/scripts/lib/prompts.js:230`). It answers *"what ran"* and **never** *"what was read"*: no slug or page identity is attached to a step. That is the direct answer to #106's provenance question about the trace — the trace pins skills, not sources; pinning *sources* is the answer citation's job (§5), and pinning *pages to raw documents* is nobody's job today (finding provenance-2).

## 5. Dimension 1 — Provenance & traceability

The vault's rule is structural and mandatory: every wiki page carries a `## Source` line back to the raw items it was built from, and every deliverable ships a `Reference.md` trace table. Kip implements the same idea at exactly one layer — the answer — and leaves the page layer, the claim layer, and the artifact layer without an enforced counterpart.

**What Kip actually does today.** The answer prompt requires inline citations pinned to the exact string the retriever supplied: *"Cite every claim back to the specific page it came from using Logseq's wikilink syntax: [[exact-page-slug]]"* (`kip/scripts/lib/prompts.js:72`). Those targets are then verified post-hoc: `extractWikilinkSlugs` slugify-normalizes every `[[target]]` (`kip/scripts/lib/roost.js:48-56`) and `extractCitedSlugs` intersects the result with `candidateSlugs`, so a link to a page that was never retrieved is detectable (`kip/scripts/lib/peck.js:169-172`, asserted in `kip/scripts/test/peck.test.js:83-87`). The app renders them as real links that peek the page in the right sidebar (`kip-app/src/main/frontend/components/chat.cljs:166`, `:296` → `kip-app/src/main/frontend/components/block.cljs:509-513`). Groom then re-audits the citation graph after the fact — broken links (`kip/scripts/groom.js:112-120`), dead ends (`:122-128`), and entity↔citing-source contradiction groups (`:227-236`) — but only for answers that were actually *filed*; an answer that stayed in chat was never a nest page, so groom never sees it.

**Where the chain breaks: the page layer.** `resolvePage` — the only nest writer — emits frontmatter as the fixed literal `{ type, created, updated, tags }` on create and touches nothing but `updated` on append (`kip/scripts/lib/pages.js:56`, `:43-45`). No source path, no content hash, no origin date. The irony is that the raw side *is* labelled: the Office converter writes `source`, `source_format`, `converted`, `conversion_notes` onto the egg with the comment *"front-matter recording the origin (so a hatched page can be traced back)"* (`kip/scripts/lib/office.js:244-260`), and web-search sources get `source: web-search`, `question`, `saved`, `backends` (`kip/scripts/lib/web-sources.js:58-66`). The hatch pipeline never copies any of it forward — `commitHatchPlan` receives the plan, source title and source content but destructures the eggs path away (`kip/scripts/lib/hatch.js:136`; the batch path carries it at `:443`, the single-file CLI drops it at `kip/scripts/hatch.js:62,81`), and writes no provenance onto a page. The only machine-readable page↔egg mapping is `hatched_sources` path→sha1 (`kip/scripts/lib/roost.js:275-285`, no page linkage) and one clucks row keyed on a **lossy humanized filename** — `humanizeFilename` drops the extension and collapses `-`/`_` (`kip/scripts/lib/hatch.js:58-61`), so `Q3_report-v2.md` becomes "Q3 Report V2": not reversible to a path, not a `[[wikilink]]`, not clickable. Kip's intended trace hub, the per-document `source` page that "links to the entity/concept pages it touches" (`kip/scripts/lib/prompts.js:372,375`), is prompt-mandated only; `hatch.js:111-113` filters candidates solely by `VALID_TYPES`, so a model that omits it hatches a document with no hub at all. The docs' provenance claim — `[[slug]]` citations "so the human can verify provenance back to the source" (`kip/docs/DESIGN.md:242-243`) — therefore over-states the code: the hop from nest page to raw document is not structural, it is whatever the LLM happened to write. (Doc fix filed as #118.)

**Claim layer.** Retrieval is whole-page: `readPageBody` returns the entire body with no offsets (`kip/scripts/lib/peck.js:112-123`), the prompt labels it only `### Page: <slug> (type: …)` (`kip/scripts/lib/prompts.js:47-51`), and the citation grammar is a page slug. There is no per-paragraph or per-block ID, and chunking is explicitly deferred (`kip/docs/DESIGN.md:208`, `kip/scripts/lib/hatch.js:29-33`).

**Artifact layer.** The vault's `Reference.md` has no counterpart. The docx/pptx skills write only the binary into `exports/` (`kip/scripts/skills/docx/run.js:62`, `:101`; no `cite|source|slug|[[` anywhere in `docx/run.js` or `pptx/run.js`, and their SKILL.md says *"It does not return the document's contents"* — the xlsx skill is a reader, not a deliverable writer). The Exports panel sees only `{name, size, mtime, ext}` (`kip-app/src/electron/electron/wiki.cljs:583-600`) — nothing records which question, turn, or nest pages produced a file. And `exports/` is not in `SOURCE_ROOTS` (`kip/scripts/lib/hatch.js:27`), so a deliverable is never re-ingested and the provenance loop never closes.

Two asymmetries inside the same codebase show these are choices rather than limits: the reminder-prep artifact persists *both* the prose brief and a structured slug list on the reminder row (`kip/scripts/reminders.js:47-61`, `kip/scripts/lib/reminders.js:230-241`), and the capture path surfaces its structured provenance in the UI as "created [[x]] · updated [[y]]" (`kip-app/src/main/frontend/components/chat.cljs:278-286`) — while the question path computes `citedSlugs` and the UI drops it (`chat.cljs:68`).

### Findings

1. **Answer-level provenance is real: mandated by prompt, verified post-hoc, rendered as clickable citations.** `kip/scripts/lib/prompts.js:72`; `roost.js:48-56`; `peck.js:169-172`; `chat.cljs:166,296` + `block.cljs:509-513`. Honest boundary: the mandate is a prompt, the verifier's output is advisory, groom re-checks only *filed* answers, and web-backed answers are held to a weaker standard — `[[wikilink]]` forbidden, "(via web search)" instead (`prompts.js:74-81`). — **[already-covered · low]**
2. **Nest pages have no source back-link, while the eggs they came from already carry provenance frontmatter.** `pages.js:56` (fixed frontmatter literal) vs `office.js:244-260` and `web-sources.js:58-66` (eggs labelled, "so a hatched page can be traced back"); `hatch.js:136` (the path is destructured away, not "in hand"); `hatch.js:58-61` (clucks key is lossy); `prompts.js:372,375` + `hatch.js:111-113` (trace hub is prompt-only and can be absent); `DESIGN.md:242-243` over-states. **Fix:** thread optional `source` / `source_hatched` through `resolvePage`, pass the eggs path the hatch call sites already resolve, prepend a `## Source` section on the `type:source` page, and synthesize that page when the model proposes none. — **[gap-candidate-feature · high] → filed as #113**
3. **The machine-readable citation list is computed and then thrown away — and an unresolvable `[[link]]` in an answer is a silent dead link.** `peck.js:259,272` computes and returns `citedSlugs`/`candidateSlugs`; `chat.cljs:68` destructures without them (`wiki.cljs:466` documents the payload; the recent-clucks panel does return `pages_touched`, but the UI never renders it); `extractCitedSlugs` only catches hallucinations *relative to candidates*, so a link matching no page at all is neither trimmed nor flagged, and `block.cljs:509-513` makes clicking it a no-op; groom's broken-link check scans nest pages only (`groom.js:112-120`). Filed answers persist only the inline links (`peck.js:185`, `:194`). **Fix:** a "Sources · 3/5 pages cited" chip row from the existing payload, plus a `## Sources` section in `fileAnswerToNest`. — **[gap-candidate-feature · medium] → filed as #117**
4. **Block-level (per-claim, per-paragraph) traceability.** Whole-page retrieval with no block IDs in the data model (`searchPages` returns `{slug, path, summary, snippet}`; `readPageBody` whole content), chunking explicitly deferred (`DESIGN.md:208`, `hatch.js:29-33`). The vault's own `## Source` line points at a whole raw document, so the pattern does not demand block-level trace; the achievable residue is findings 2 and 3 plus the FTS `snippet()` pointer (#115). — **[out-of-scope · low]** *Why it does not apply: the pattern's mandate is document-level, Kip's data model has no spans to cite, and building a chunk store is the one thing DESIGN.md §8 already rejected for now.*
5. **Output-layer provenance: `exports/` deliverables carry no source trace and sit outside the wiki loop.** `docx/run.js:62,:101` (binary only, no sidecar), `wiki.cljs:583-600` (`{name,size,mtime,ext}`), `hatch.js:27` (`exports/` not in `SOURCE_ROOTS`). **Fix:** prompt-level first — require the skill-turn answer to end with a `Sources: [[slug]] …` block; stronger version writes a hatchable `<name>.sources.md` sidecar; cheapest single step is adding `'exports'` to `SOURCE_ROOTS` so a deliverable can be hatched back. — **[gap-candidate-feature · low]** *Runner-up for triage (§14).*

## 6. Dimension 2 — Synthesis vs restatement

The vault's rule is explicit: *synthesis is preferred over restatement — a good wiki page compares and contrasts across multiple raw items rather than paraphrasing one file.* Kip's code does the opposite at ingest, leaves it unspecified at query time, and implements the compare/contrast half only in a read-only linter.

**Hatch (↔ Ingest) is per-file and nest-blind.** `proposeAndDraftPages` is sent `Source title: <humanized filename>\n\n<whole file>` and nothing else (`kip/scripts/lib/prompts.js:397-398`; same for the classic proposer at `:306`). It never sees an existing page, a slug list, a tag list, or an index — so page titles are invented per file and the only cross-source mechanisms are (a) `findSimilarSlug` over slug *strings* (`kip/scripts/lib/roost.js:161-175`) and (b) whatever `[[wikilinks]]` the model invents by applying the slug rule itself (`prompts.js:377`). `hatchAllSources` processes files strictly serially (`kip/scripts/lib/hatch.js:422-455`), so the only cross-file effect is incidental: DB rows from earlier files are visible to later `findSimilarSlug` lookups. **On the default path, an "update" is a body drafted without knowledge of the page it is appended to** — see finding 1. The one exception is whiteboards: `findRelatedPages` runs an FTS match per node label and hands up to 12 existing page slugs+summaries to `describeWhiteboard` (`hatch.js:201-213`), whose prompt says "do NOT just restate the outline" and asks for tension, imbalance and gaps (`prompts.js:446-458`). That is the only genuine cross-source synthesis write in the repo — and note it links across sources rather than synthesizing their *content* (it receives slugs and one-line summaries, never bodies).

**Peck (↔ Query) has multi-source context but no synthesis mandate.** `formatPagesForPrompt` dumps the full body of every candidate — up to 10 direct + 15 broad FTS hits, deduped by slug — into a single completion (`prompts.js:47-51`, `peck.js:28,147,159`; the 4096 figure is the *output* cap, `prompts.js:93` — the input has no cap at all, which is also a cost exposure: see §14, input budget). So the model genuinely reasons over many pages at once: the mechanical precondition for synthesis is **already covered**. What is missing is any instruction to use it that way. `ANSWER_SYSTEM_PROMPT` (`prompts.js:62-72`) says "Answer using ONLY the information in these pages", "do not speculate", and "Cite every claim back to the specific page it came from" — an attribution rule, not a synthesis rule. There is no compare/contrast instruction and, more consequentially, no rule for disagreement: when two retrieved pages state different values, the prompt's only escape hatch is the `NO_ANSWER` token for "pages don't contain enough to answer", so the model silently picks one and cites it, and the citation makes the choice look authoritative. Groom *detects* exactly this condition (`flagContradictions`, `prompts.js:270-287`) but its findings never reach the answer path (finding 2 here; §9's finding 1 is the bridge). The bounded skill loop is the only multi-step behavior in a turn, and it is aimed outward — web search, document generation — never at deeper nest retrieval (finding 3).

**Groom (↔ Lint) is the strongest leg of the mapping and the closest thing to the vault's compare/contrast ideal.** `flagContradictions` (across pages, grouped by type/tags), `reviewPageCoherence` (within a page's `_Update_` stack: internal contradiction, redundancy, superseded claim, plus a `consolidate` verdict), and `checkPagesSameSubject` (merge candidates the slug check missed) are all literally compare-across-multiple-items passes (`prompts.js:270-287,485-502,531-541`). They are also strictly report-only: the only files groom writes are `.roost/groom-report.md` and progress/metrics JSON (`kip/scripts/groom.js:377-422`), and the app renders the verdicts as inert text — `(consider consolidating)` at `kip-app/src/main/frontend/components/wiki_status.cljs:112`, with no apply/accept action anywhere (grep for `consolidat` across `kip-app/src` returns only that line).

### Findings

1. **Default hatch appends a blindly-drafted body — the contradiction-aware update prompt is unreachable on the default path.** In `commitHatchPlan`, a combined-path body is returned verbatim and `generatePageContent` is never called (`hatch.js:142-143`), and the combined filter requires a non-empty body so the fallback generate is unreachable for valid candidates (`:111-113`). Therefore `buildGenerateContentSystemPrompt`'s `update` branch — which carries the only cross-source synthesis instruction in the write path, "If the new information contradicts something already on the page, state the contradiction explicitly… the page should read as a history of what's known" (`prompts.js:328-336`) — never runs on the default path (it *does* still run under `--classic` / `KIP_HATCH_CLASSIC=1` / the app's Classic checkbox, which defaults false and is labelled "slower; for comparison", `kip-app/src/main/frontend/components/ingest.cljs:263,416` — so "dead code" would overstate it). `PROPOSE_AND_DRAFT_SYSTEM_PROMPT` never mentions the existing page at all (`prompts.js:367-380`), and `resolvePage` appends whatever was drafted under `_Update <date>:_` (`kip/scripts/lib/pages.js:44`). Net effect: the default ingest manufactures the redundancy and superseded-claim patterns that groom's coherence check then has to find (`needsCoherenceReview` triggers at ≥2 `_Update` markers or >1500 chars, `groom.js:267-268`). DESIGN.md §8 does not defer this; DESIGN.md:134-135 ("Reconciling those sections is Groom's job") defers *reconciliation*, not *awareness of what you are appending to*. — **[gap-candidate-feature · high] → filed as #114**
2. **The answer prompt mandates per-page citation but never asks for cross-page comparison, and has no rule for disagreement.** Evidence as above (`prompts.js:62-72` vs `:270-287`). The mechanical multi-page context is already covered; the instruction layer is not, and the fix is a prompt string. — **[gap-candidate-feature · high] → filed as part of #116**
3. **No multi-hop path: the skill loop can reach the web but never the nest, and outbound `[[wikilinks]]` are never followed.** `searchPages` is called only from `lib/peck.js:147,159`, `lib/hatch.js:207` and `scripts/reminders.js:49`; `kip-control`'s OPERATIONS enum exposes hatch/groom/rebuild-roost but no search (`kip/scripts/skills/kip-control/run.js:18-22`). Peck uses `extractWikilinkSlugs` only on its own answer text for citation accounting (`peck.js:169-172`), never to walk a retrieved page's outbound links (groom does walk them, for lint — `groom.js:116,152,256`). Compounding this, the tool loop is entered only when `mightNeedSkill` is true — `pageCount < 2` or a hint regex (`peck.js:50-52,214`) — so a rich initial retrieval, the normal multi-hop case, never gets a second retrieval chance. A question whose answer spans page A and the page A links to (but that shares no token with the question) is unreachable. Related: kip#34/#37 (router / query planning) attack the neighbouring cost problem. — **[gap-candidate-feature · medium]** *Runner-up for triage (§14).*
4. **Compare/contrast synthesis already exists as code — in Groom's checks and the whiteboard Context prompt.** `flagContradictions`, `reviewPageCoherence` (with its `consolidate` verdict), `checkPagesSameSubject`, `describeWhiteboard`'s explicit anti-restatement instruction, and `captureFacts`' multi-page-aware "PREFER updating an existing relevant page" routing (`prompts.js:549-560`) together show the vault's synthesis primitive is implemented and idiomatic in this codebase. What is absent is a write path from any of them back into a page — which is exactly what findings 1 and 2 address, so no separate feature is warranted. Note also that the one artifact that *is* a cross-page synthesis (a filed Peck answer) is stored as a `**Q:** …` transcript appended under an `_Update_`, i.e. restatement-shaped even when the answer synthesized. — **[already-covered · low]**

## 7. Dimension 3 — Index-first querying

**The vault rule:** a query reads the wiki INDEX first, then descends into raw items only where the index points. The index is an LLM-owned synthesis artifact — one line per page, carrying enough meaning that the querier can decide where to go without opening a raw file.

**Kip's reality:** strictly index-first in the mechanical sense, and not at all in the synthesis sense.

### What Peck actually queries

Retrieval is one SQLite FTS5 `MATCH` over `pages_fts(slug, body)` in `<coop>/.roost/meta.db`, ordered by bm25 `rank`, with a `snippet()` computed per row (`kip/scripts/lib/roost.js:122-154`). There are no embeddings, no vectors, and no graph walk. `toMatchQuery` splits the question on whitespace, quotes each term, and OR-combines them (`roost.js:16-23`), so a natural-language question still matches. The FTS5 table uses the default `unicode61` tokenizer with no porter stemming and no stopword table (`kip/scripts/lib/db.js:17-20`), so morphological variants miss.

Candidates are picked by the index; page bodies are read from disk only afterward, and a candidate whose `.md` is missing is dropped with a warning rather than crashing the turn (`peck.js:112-128,399-400`). The app never opens `meta.db` at all — it shells out to the same scripts (`kip-app/src/electron/electron/wiki.cljs:14-25`).

### What index artifacts exist

Two, with opposite roles:

1. **`meta.db` (pages + pages_fts)** — the real index. `pages` carries an LLM-written one-line `summary` per page, requested from the hatch model as `"summary": "one-line description"` (`prompts.js:297,380`) and written at `hatch.js:184`. There are no per-type index files — `regenerateIndexMd` writes a *single* `nest/index.md` (`roost.js:228,239-252`).
2. **`nest/index.md`** — a mechanical alphabetical listing (`ORDER BY type, slug`, `roost.js:223`), one line per page that *embeds the per-page LLM summary* (`roost.js:248`). Its own header says it is "a browsing aid for humans in Kip, not read by any script" (`roost.js:236-237`). Verified: the only readers in either repo are tests (`scripts/test/roost.test.js:131`, `hatch.test.js:139-148`, `peck.test.js:106`) and the app's nest-page counter, which explicitly *excludes* it (`wiki.cljs:423,434`). No component renders it; it is also unreachable from the app UI, so even its stated purpose as a human browsing aid is only met outside Kip.

### The summary layer is already built — and Peck throws it away

This is the sharpest finding on this dimension. `searchPages` returns `summary` and `snippet` for every candidate, plus bm25 ordering (`roost.js:130-131,150`). `retrieveCandidates` passes those objects straight through (`peck.js:165`). Then `readPageBody` rebuilds each candidate as `{slug, path, type, content}` — dropping the summary, the snippet, and the rank (`peck.js:121-123`) — and `formatPagesForPrompt` sends only `### Page: <slug> (type: …)` followed by the verbatim body (`prompts.js:47-51`). So Kip's Layer-2 index is populated at ingest, returned by the query, and discarded three lines before the prompt. The answering model gets the one artifact the vault says to read first in the one place the vault says not to send it: the raw dump.

The codebase already contains the vault's move, twice, just never in the Peck answer path: `scripts/reminders.js:49-51` builds its LLM prompt from `h.snippet || h.summary` and never opens a nest file — index-read-first, verbatim; `describeWhiteboard` consumes a `[{slug, summary}]` index read to decide which existing pages a board refers to (`prompts.js:463-474`, fed by `hatch.js:207`).

### The gate that defeats reformulation

`extractKeyTerms` — the only query reformulation in the system, and the only thing that can bridge a vocabulary mismatch the tokenizer cannot — runs only when the direct pass returns fewer than `DIRECT_HIT_CONFIDENCE = 3` rows (`peck.js:37,152`). Because `toMatchQuery` OR-combines *every* token including "what", "do", "i", "know" and "about", and FTS5 has no stopword list, any English question matches three-plus pages on filler alone. In any nest beyond a handful of pages the key-term pass is skipped exactly when the nest is large enough for vocabulary mismatch to matter. (The test that asserts the skip, `peck.test.js:545-561`, uses a degenerate 4-page nest where every page is about sleep — the one case where skipping is safe.) It also caps candidates at the default `LIMIT 10` in the common case, so `BROAD_SEARCH_LIMIT = 15` is mostly theoretical. Note the docs describe this pass as unconditional: "plus a second pass on key terms an LLM extracts from it — unioned for recall" (`kip/docs/DESIGN.md:239-240`). That is not what the code does. Related: kip#34/#37.

Worse, Kip's response to thin retrieval is to reach for a *skill*, not a better read of the index: `mightNeedSkill` fires on `pageCount < 2` (`peck.js:50-52`). When the index comes back unhelpful, Kip goes to the web — the exact inversion of the vault's rule.

### Would reading an index first change quality or cost?

Yes on both, and most of it is already paid for. **Cost:** the answer prompt carries the full body of up to 10 candidates — with no input cap — into one completion; a summary line is ~25 tokens per page, and the zero-round-trip variant costs ~250 tokens against 5k-30k-token prompts. **Quality:** bm25 over OR-expanded filler is the only relevance signal, and the model currently has to infer what a page is *about* from an append-grown body plus a slug heading; the summary is precisely the "what this page is" line. **The prerequisite:** the summary is stale by construction — hatch overwrites it with each ingest's newest one-liner while the body appends (`hatch.js:184`), and `rebuild-roost` silently degrades it to the first non-heading paragraph truncated at 200 chars (`scripts/rebuild-roost.js:12-19,43`). Groom's deep pass already computes a better one and throws it into a checklist (`groom.js:344` pushes `suggested` into the report only). Making the index usable as an index means closing that loop, which groom has already done the analysis for.

### Findings

1. **The per-page LLM summary index already exists and is returned by every query — Peck discards it before the prompt.** Thread `summary` (and `snippet`) through `readPageBody` into `formatPagesForPrompt` as a one-line digest; optionally add a summary-only select stage that reads full bodies for a chosen subset. Prerequisite: let hatch/groom maintain the summary instead of degrading it on rebuild. Related: kip#35/#36 (this also bounds the input-budget exposure). — **[gap-candidate-feature · high] → filed as #115**
2. **`extractKeyTerms` is effectively unreachable:** OR-expansion with no stopword removal defeats the `< 3` row-count gate, so the only paraphrase bridging in the system is skipped in any nest of nontrivial size, and candidates cap at 10. Fix deterministically in `toMatchQuery` (stopword strip, no LLM call) and re-gate on non-stopword hit count or top bm25 rank. — **[gap-candidate-feature · high]** *Runner-up for triage (§14); overlaps kip#34/#37.*
3. **`nest/index.md` is a write-only artifact, and that is the documented design.** Kip's index-first property is carried by `pages_fts`, which genuinely is read before any raw file; the artifact already embeds the summary layer (`roost.js:248`) — it is just read by nobody. Making index.md machine-readable would add a third competing index without changing what the model sees; the deficiency is the DB summary layer's maintenance, not the markdown. — **[already-covered · low]**
4. **The index read is invisible to the human:** `candidateSlugs` and `citedSlugs` cross the IPC boundary and are destructured away at `chat.cljs:68`. The gap between them is exactly the signal that retrieval was too broad, and the data is already in hand. — **[gap-candidate-feature · medium] → filed as #117** *(same mechanism as §5 finding 3 — one item, one fix.)*

## 8. Dimension 4 — Persistence of results

**The vault pattern.** Every synthesis becomes a wiki page — the page is the durable artifact: frontmatter, a `## Source` line, written into the same namespace queries read. Nothing the counterpart calls "an answer" is allowed to live only in a chat transcript.

**Kip today.** Peck has exactly one function that persists an answer, and it is complete and tested — just unreachable from the app.

`fileAnswerToNest` (`kip/scripts/lib/peck.js:179-197`) writes the answer as a `concept` page ("closest fit of the three"), tagged `['from-peck']`, with body `**Q:** <question>\n\n<answer>` (`peck.js:181-186`), through the same `resolvePage` create-vs-update resolution Hatch uses; it then re-reads the file, `upsertPage`s it into `meta.db`, regenerates `nest/index.md`, and appends one `peck` clucks entry listing candidate slugs plus the new slug. Two provenance properties fall out for free that the vault mandates explicitly: the question is restated verbatim as the page's opening line, and the answer's `[[slug]]` citations survive into the stored markdown, so the filed page links forward to the pages it was built from. What it does *not* do: un-cited `candidateSlugs` go only to the clucks log, cited pages gain no back-pointer, and there is no `source:`-style frontmatter key naming where the synthesis came from.

**When it fires.** Only under `fileToNest && answer && !webbed` (`peck.js:260-262`). Three gates stack on top:

- `peckTurn`'s default is `fileToNest: false` (`peck.js:391`). `askQuestion`'s `fileToNest: true` default (`peck.js:369`) is dead in production — only the tests call `askQuestion`.
- `scripts/chat.js`, the app's backend, passes `fileToNest: false` explicitly (`kip/scripts/chat.js:126`) and never imports `fileAnswerToNest`. Its argv parser knows only `--trace`, `--arena-compare-to` and `--history` (`chat.js:45,69-89`) — **there is no flag that could turn filing on**, so this is not a hidden switch but a missing one.
- The CLI is the only surface: `scripts/peck.js` prints the answer then asks `y/n` (`kip/scripts/peck.js:83-97`), and declines to offer at all when `candidateSlugs` is empty (`:78-81`) — so a web-backed or skill-only answer can never be filed. Declining still logs `peck` with the candidates (`:92`).

The IPC chain forwards nothing more: `:wikiChat` passes only `trace?`/`arena-compare-to`/`history` (`kip-app/src/electron/electron/handler.cljs:615-616`) into `wiki/peck!`, whose argv builder cannot express the option and whose docstring says so ("Runs the Peck workflow for `question` **without filing the answer back**", `kip-app/src/electron/electron/wiki.cljs:465,476-480`). In the renderer, `turn->message` destructures `{:keys [intent answer learned note pages steps callId arenaId webSource]}` — `citedSlugs` and `candidateSlugs` are dropped on the floor (`chat.cljs:68`), and the settled answer bubble renders exactly five affordances: steps line, markdown body, web-source save, A/B verdict, 👍/👎, Regenerate (`chat.cljs:289-314`). No save control.

**The mirror-image half.** Statements always persist, from both surfaces, with no confirmation: `peckTurn` documents that `fileToNest` "only affects the question path… a statement is always filed — that's the point" (`peck.js:381-382`), and the statement branch runs `captureFacts` → `fileCapturedFacts` → one `told` log entry unconditionally (`peck.js:403-411`). The app surfaces it as "✓ Learned — updated [[companyx]]" (`chat.cljs:277-285`). So the vault's mapping inverts in an interesting way: Kip auto-persists the *low*-synthesis content (a restated fact) and never persists the *high*-synthesis content (a cross-page answer). (Strictly, a statement that captures nothing new writes no page and logs `told` with an empty slug list — "always persist" means "always files".)

**Where the answer goes instead: nowhere.** The conversation lives in `defonce *peck-session`, documented "Not persisted across restarts" (`chat.cljs:42-45`). `chat.js` nulls the streamed answer when the turn ends (`chat.js:127`); `peck-metrics.json` is content-free by construction (`lib/run-progress.js:46-61,74-80`); and `peck-trace.jsonl`, the only artifact that carries full answer text, is unreachable from the app *UI* (`chat.cljs:120` hardcodes `false`) though `KIP_PECK_TRACE=1` reaches it via the inherited environment. And because neither `fileAnswerToNest` nor the CLI's decline branch runs on this path, an app question turn writes **no `log`/clucks row at all** — `appendLog('peck', …)` exists only at `lib/peck.js:194` and `scripts/peck.js:92`. `kip/docs/DESIGN.md:246-247` lists that log write as step 4 of the question flow; on the app path it never happens. The vault's weakest guarantee (the synthesis is at least *recorded*) is not met.

**The precedent that proves it's cheap.** Kip already ships the exact affordance pattern for a different artifact: when a turn runs web search, `buildWebSource` renders the results into a front-matter'd Markdown doc (`lib/web-sources.js:51-80`) and the app offers "↓ Save these web results as a source", which writes it into `eggs/` via `:wikiAddEgg` (`chat.cljs:235-262`). The raw search results get a one-click keep; the synthesized answer above them does not.

### Findings

1. **`fileAnswerToNest` is complete, tested, and unreachable from the app — even by flag.** `chat.js` has no `--file-to-nest` flag to flip (`chat.js:45,69-89`), `wiki/peck!` cannot express one (`wiki.cljs:476-480`), the renderer discards the inputs the call needs (`chat.cljs:68`), and the answer bubble has no save control (`chat.cljs:289-314`). A post-hoc entrypoint is required rather than flipping the flag, because today filing happens *inside* the turn (`peck.js:261`) — before the human has read the answer. `fileAnswerToNest` is already exported (`peck.js:420`) and is exactly the post-hoc primitive. Not on DESIGN.md §8's deferred list; only *auto*-filing is deferred (`kip/docs/DEVELOPMENT.md:631`), which a manual one-click does not contradict. — **[gap-candidate-feature · high] → filed as #112**
2. **An app question turn leaves no durable record of any kind — not even the audit entry the CLI writes.** No `appendLog('peck')` on the chat.js path, the conversation atom is `defonce` and lost on restart (`chat.cljs:42-45`), the progress file nulls the answer (`chat.js:127`), and metrics are content-free. Writing the same `peck` clucks entry the CLI writes on decline (`scripts/peck.js:92`) is a one-line fix and gives the vault's "un-ingested raw" lint an analogue: questions asked but never kept become a visible backlog. — **[gap-candidate-feature · medium] → filed as part of #112**
3. **The file-back that exists is not fit to be exposed.** (a) The page title is the raw question and `slugify` has no length cap (`roost.js:30-39`; contrast the 60-char cap in `lib/web-sources.js:9,16`), so a ~256+ character question fails the write with ENAMETOOLONG and nothing catches it (`pages.js:50-57`). (b) The question is passed as the DB `summary` on both branches (`peck.js:192`) and `upsertPage` overwrites `summary` unconditionally (`roost.js:100`), so filing onto an existing page replaces hatch's curated one-liner — which `regenerateIndexMd` then renders as the page's index description (`roost.js:248`). (c) The update branch returns the existing page's type and tags and discards the candidate's (`pages.js:43-47`), so `from-peck` is silently dropped and a peck-written answer is unmarkable in frontmatter. Untested: `peck.test.js:90-126` asserts only action/slug/body. — **[gap-candidate-feature · medium] → filed as part of #112** *(must land before or with the control that exposes it)*
4. **The asymmetry itself is deliberate and matches the vault's ownership split only partially.** Statements always file on both surfaces with no confirmation (`peck.js:381-382,403-411`), rendered as "✓ Learned" (`chat.cljs:277-285`). This is the reference implementation the answer path should reuse — same `resolvePage`, same dedup invariant, same index mirror — so the file-back feature is a surface change plus one JSON entrypoint, not new storage. — **[already-covered · medium]**
5. **Dedup for a filed answer is keyed on the question, not the subject.** `resolvePage` compares `slugify(question)` against existing slugs at 0.45 (`pages.js:26-29`), and a natural-language question rarely lands within 0.45 of the subject page it drew from — so re-asking a topic in different words grows the nest, and the only backstop is groom's read-only near-duplicate report (`groom.js:96-108`). Cheapest fix: when `citedSlugs` has exactly one member, default the file-back to appending under a dated `_Update_` on that page (the filed body already embeds `[[cited-slug]]` links forward, `peck.js:185`). — **[gap-candidate-feature · low] → filed as part of #112** (follow-up)

## 9. Dimension 5 — Lint / health (groom ↔ vault Lint)

The vault's `groom ↔ Lint` half of the mapping is **accurate and is the strongest of the three**: Groom is a real, dedicated, periodic health checker, and it is *more* thorough than the vault's three named checks. Where Kip falls short of the pattern is not in what it checks but in **who gets to see the answers** — lint output stops at a modal and a checklist file, while the vault's Lint is a maintenance loop over a wiki that Claude actively reads and writes.

### What groom actually checks (verified against `kip/scripts/groom.js`)

Quick mode (`runGroom`, `groom.js:306-315`) runs four: orphans (`:53-67`), meta.db↔disk drift (`:70-94`), near-duplicate slugs at the same 0.45 threshold the writer uses (`:96-109`), and one LLM contradiction pass over same-type groups of ≤6 (`:172-224`). Deep adds seven: broken links (`:112-120`), dead-end pages (`:123-128`), page coherence over multi-`_Update_` bodies (`:267-269`, `:333-338`), summary drift (`:340-345`), missing links (deterministic prose scan then LLM confirm, `:142-165`, `:347-353`), merge candidates (`:239-265`, `:355-362`), and a wider contradiction sweep that groups each entity/concept with the source pages citing it (`:227-236`, `:364-371`). (Counting rule: 4 quick + 7 deep = 11 checks at run level, implemented by ten `find*`/`build*` functions in groom.js plus four prompt-side LLM checks.) Every finding is a `- [ ]` suggestion in `.roost/groom-report.md` (`:377-421`); grep confirms the only nest-adjacent writes in the file are `fs.mkdirSync(.roost)` and the report `writeFileSync` (`:418,420`), matching the docs' "Groom writes no page" (`kip/docs/DESIGN.md:289`).

### Check-by-check against the vault's three

**Contradictions — covered, the best match.** Quick and deep both run `flagContradictions` (`prompts.js:268-281`), and deep's coherence prompt explicitly targets "internal contradiction … superseded claim" across `_Update_` sections (`prompts.js:486-496`) — precisely the reconciliation Hatch defers. Two coverage edges the vault pattern doesn't have: grouping is same-type only and a type with a single page is dropped entirely (`groom.js:181`), so a small coop with one page per type gets **zero** contradiction checking in quick mode; and an entity↔concept pair is never grouped directly — deep's cross-groups are entity/concept plus its *citing sources* (`groom.js:228-233`), so a conflict between two concepts is only reachable indirectly through a source that cites both.

**Orphan pages — covered, and manufactured by Peck.** `findOrphans` is the vault check verbatim. But Kip's own persistence flow guarantees the finding: `fileAnswerToNest` writes a concept page whose only links point *outward* to the pages it cited (`peck.js:180-188`), and Hatch's combined prompt tells the model to cross-link only "the other pages you are creating in this same batch" (`prompts.js:377`) — so no code path ever writes an inbound link to a filed answer. Every CLI-filed answer lands in the next groom's orphan list by construction. The `from-peck` tag (`peck.js:186`) marks these pages and is read by nothing in either repo (single grep hit), so neither groom nor the UI can distinguish "orphaned synthesis worth keeping" from "orphaned cruft".

**Un-ingested raw — covered, but by Hatch, not lint, and blurred.** The vault distinguishes "raw item with no wiki page". Kip's `pending` count is that check, surfaced as a bare number in Coop status (`wiki_status.cljs:38-40,142-145`) rather than as a groom finding. The blur: `pending` is documented as "new OR content-changed since last hatch" (`hatch.js:318`), and the hash comparison at `hatch.js:359` already holds the prior sha1 keyed by the same path, so the two cases are separable for free — but they collapse into one bucket. A user who edits an "immutable" egg (`GETTING-STARTED.md:236`) looks identical to one who dropped in a new file, and the re-hatch that follows is exactly what produces the duplicate `_Update_` stacks groom's coherence check then has to catch after the fact.

**Stale metadata / dangling cites — dangling cites are covered (deep only, `groom.js:112-120`, date-shaped targets correctly exempted at `:47-50`); type/tag drift is not.** Groom never parses frontmatter: type/tags/summary come from the `pages` table and bodies from `pages_fts` (`groom.js:297-299`). Summary drift *is* shipped (deep only, `groom.js:340-345` — see §7). Type and tags, though, are write-once in practice: on update, `resolvePage` keeps the existing file's frontmatter and bumps only `updated` (`pages.js:43-45`), and `upsertPage` writes the existing row's values back (`roost.js:99-100`). So a page whose subject drifted keeps its creation-time tags forever, and since `findSimilarSlug` ignores type (`roost.js:161-175`), a source hatched onto a lexically similar concept page keeps the wrong type. (A *hand-edited* `type:` does propagate to meta.db on the next update — `pages.js:47` reads it from the file — but nothing ever prompts one.)

**Peck surfacing lint at answer time — absent.** This is the real gap. `citedSlugs` is computed and returned (`peck.js:259`) but nothing joins it against lint state; the Peck panel contains no reference to groom at all (grep of `chat.cljs` for "groom" is empty). The standing bridges into the skill loop are `SKILL_HINT_RE` — which includes the literal words hatch/groom/rebuild-roost/coop status (`peck.js:45-50`) — and `pageCount < 2` (`:50-52`); neither attaches findings to the answer that cited the flagged page. So an answer cited from a page groom flagged as contradicted, orphaned, or a near-duplicate is delivered with no hint — the exact case where the vault's Lint concept would earn its keep, and the checks that would detect it (orphans, near-dupes, drift) are deterministic and cheap.

**Cadence — inverted priorities, and the scheduled pass can silently not happen.** Only deep is scheduled (`kip-app/src/electron/electron/groom_scheduler.cljs:51` fires `wiki/groom-deep!`); the fast deterministic pass is manual-only, and it persists only a counts-only summary line (`groom.js:505-513`) — no findings list, and it does not update "Last groom", which reads only `groom-metrics.json` (`wiki.cljs:462`), so the overview says "never" after a successful quick run. Worse, the deep run is recorded as done before it is: `:groom/last-run` is stamped at fire time (`groom_scheduler.cljs:47`), per-graph failures are swallowed (`:52`), and the notification says "finished" unconditionally (`:58`) — while the four per-page deep loops have no try/catch (`groom.js:334-362`) and `callLLM` rethrows (`lib/llm.js:210`), so one transport failure aborts before `writeGroomReport` (`groom.js:489-492`). A user watching the progress poll would see it stall (`groom-progress.json` is written continuously, `groom.js:480-486`), but nothing notifies, no report or metrics land, and Coop status shows the run as done for another week. Only the contradiction passes are fault-isolated (`groom.js:216-222`, `:369`).

### Findings

1. **Peck answers carry no lint signal — the standing bridges (a name-triggered skill, thin retrieval) never attach findings to an answer.** Join groom's deterministic findings against `citedSlugs` and surface a muted advisory line under the answer; the prerequisite artifact (`.roost/lint.json`) is one write in groom's existing report path. — **[gap-candidate-feature · high] → filed as #116**
2. **The only scheduled lint can silently produce nothing and is recorded as done anyway.** Stamp `:groom/last-run` on success, guard the deep loops, report failures. — **[gap-candidate-feature · high]** *Runner-up for triage (§14); reliability bug rather than feature.*
3. **A changed raw file is indistinguishable from a new one**, hiding immutability violations and pre-empting the duplicate-`_Update_` problem. Add a `changed` bucket — it is one `hashes.has(relPath)` away. — **[gap-candidate-feature · medium] → filed as part of #113**
4. **Quick groom persists only a counts-only log row — no findings list, never scheduled, and it does not move "Last groom".** Persist a slim findings artifact (or read the last quick run's row back from the existing log table) and let the timestamp reflect any completed run. — **[gap-candidate-feature · medium]** *Runner-up for triage (§14).*
5. **No lint checks type/tag metadata drift** (summary drift is already shipped). Mirror it with a metadata-drift check in deep mode. — **[gap-candidate-feature · low]** *Runner-up for triage (§14).*

Not proposed: auto-applying groom findings. The vault's Lint is run by the same agent that owns the wiki layer, so "fix it" is natural there; Kip's nest is explicitly human-owned and DESIGN.md §5.3 commits to read-only grooming (`DESIGN.md:264-291`). Every recommendation above stays on the report side. Also noted but not actioned: `DESIGN.md:265-266` describes quick groom as "`meta.db` only" while `findDrift` walks `nest/` subdirectories on disk (`groom.js:70-91`) — doc/code mismatch, folded into #118.

## 10. Dimension 6 — Immutable raw vs mutable graph

**The mapping.** The `hatch ↔ Ingest, peck ↔ Query, groom ↔ Lint` framing holds, but the *layer* mapping is where the two models actually differ. Vault: `1.Raw` (immutable inbox) → `2.Wiki` (Claude-owned, rewritten freely) → `3.Templates` → `4.Output` (human-owned). Kip: `eggs/` (+ `journals/`, `pages/`, `whiteboards/`) → `nest/` → `.roost/` (derived) → `exports/` + `.roost/groom-report.md`. Two inversions matter. First, Kip's wiki layer is **append-only** where the vault's is rewrite-owned: `resolvePage` never rewrites existing prose, it appends `\n\n---\n_Update <date>:_\n\n<body>\n` and keeps the old type and tags (`pages.js:44-47`). Second, ownership is shared rather than assigned — the human owns raw *and* co-edits the wiki, because `nest/*.md` are ordinary Logseq pages inside the open graph (`DESIGN.md:451-454`).

### What the code actually does

| Vault rule | Kip reality | Verdict |
|---|---|---|
| `1.Raw` immutable, never edited after capture | Documented convention only: `GETTING-STARTED.md:93` ("Treat eggs as **read-only**"), `:236` ("Eggs are meant to be immutable. If a source changes, drop the new version in with a new filename"), `DESIGN.md:50`. No chmod, no at-rest checksum verification, no tamper detection. But there **is** a change detector the vault lacks: `hatched_sources` stores sha1(path-relative file) and `collectPendingSources` skips unchanged files (`lib/db.js:31-37`, `lib/hatch.js:359`; hash computed at `:428`, written via `roost.js:275-285`). That hash is a *re-derivation trigger*, not an immutability guard. | weaker than vault, but not unmechanised |
| `2.Wiki` owned by Claude, freely rewritten | Only three nest writers exist: `resolvePage` (`pages.js:45,57`), `hatchWhiteboard` (`hatch.js:265`) and `regenerateIndexMd` (`roost.js:256`). Updates append; nothing deletes or rewrites prose (the whiteboard source page is the one full-replace path, deliberately, and the page itself says "Edit the board, not this page" — `hatch.js:216-226,259-265`). | stronger (safer), at the cost of pushing all reconciliation to a report-only groom |
| Human owns Raw and Output; never edits the wiki | nest pages are editable in the app like any Logseq page. Note on the premise "no hash-check on eggs": that is not accurate. There *is* a sha1 content check per source, and it is what makes re-hatching idempotent. What is missing is everything *around* the hash — no detection/warning, no revision lineage, and no reverse map from a raw file to the pages it produced.

### Findings

1. **"Eggs are immutable" is unenforced, and Kip's only response to a raw edit is a full-content re-append with no revision lineage — high.** The documented versioning workflow guarantees the worst case. `GETTING-STARTED.md:236` says to drop a changed source in *under a new filename*; because `hatched_sources` is keyed by path (`roost.js:275-285`) the new file is wholly pending, and the old row is never pruned (no `DELETE FROM hatched_sources` anywhere in kip/scripts). The combined draft call sees only `Source title: …\n\n<file>` (`prompts.js:397-398`) — no existing page content, no prior version — so `resolvePage` appends essentially the whole document again under a new `_Update_` (`pages.js:44`). Editing an egg in place does the same thing by way of the hash change. The Hatch preview cannot warn, because it renders only `{source, kind, kb}` and never distinguishes new from changed (`hatch.js:378-384`, `ingest.cljs:410-412`). The classic path already has the hook needed to fix this — `existingContent` is read and passed to `generatePageContent` there (`hatch.js:145-152`) — it is just never used by the default path. *Backlog: source revision handling (lineage frontmatter, delta drafting on re-hatch, superseded-row marking, "changed" badge in the preview) — filed as #113, merged with §9 finding 3 (same changed/new split and lineage key).*
2. **`meta.db` is load-bearing state the Markdown cannot reconstruct, so "delete the database and rebuild it from the files" (`DESIGN.md:32-34,109-110`) is only half true — and the half that fails is the dedup memory — high.** `rebuildRoost` touches only `pages`, `pages_fts` and `index.md` (`scripts/rebuild-roost.js:22-68`); it never reconstructs `hatched_sources`, and `pages.summary` is not in the frontmatter `resolvePage` writes (`pages.js:56`), so a rebuild silently downgrades every LLM summary to `deriveSummary`'s first-paragraph extract (`rebuild-roost.js:43`) and weakens groom's summary-drift check. Delete `meta.db` and `findSimilarSlug` — which reads only the DB (`lib/roost.js:161-175`; call sites `lib/hatch.js:77`, `lib/pages.js:27`) — returns null for every title, so the next hatch *creates* near-duplicate pages instead of updating: precisely the failure mode DESIGN.md §4.3 calls the single most important invariant to prevent. The same applies to a second machine: Dropbox sync excludes `.roost/` while syncing `eggs/`, `nest/` and `clucks/` (`kip-app/src/electron/electron/dropbox_sync.cljs:34`), so the hash memory never travels with the graph the user is actually editing. The vault has no analogous failure because both its raw and wiki layers are plain Markdown. *Backlog: make the index honestly derived — `summary:` + source lineage in page frontmatter, and a rebuild story for `hatched_sources` (or stop claiming it is derived) — filed across #113 (lineage/summary frontmatter) and #115 (summary maintenance).*
3. **The human co-edits the wiki layer, and the machine neither re-indexes nor detects hand edits.** *(This finding was narrowed during verification: its original "crash or resurrect" claims were refuted — batch hatch wraps each file in try/catch and continues (`hatch.js:427,451-453`, the error surfaces per-file in the ingest UI at `ingest.cljs:396-398`), and both CLIs exit cleanly with `err.message` (`scripts/hatch.js:88-91`). The retrieval path is even hardened against missing files (`readPageBody` returns null with a "Run rebuild-roost" warning, `lib/peck.js:110-128`).)* The surviving defect is real but narrower: (a) only `upsertPage` writes `pages_fts` (`roost.js:111-112`), so a hand edit is invisible to Peck until that page is touched again or a manual rebuild runs — and `rebuild-roost` is reachable only from a terminal or via the kip-control skill (zero references in `kip-app/src`), even though the drift report's own suggested fix is `npm run rebuild-roost` (`groom.js:413,450`); (b) groom's `findDrift` compares slug *sets* only and never hashes content (`groom.js:70-91`), so a hand edit produces no finding; (c) the write *target* comes from the DB row rather than from disk (`pages.js:33,38`), so a renamed/deleted page makes the unguarded Peck statement path throw ENOENT (`lib/peck.js:339,346,196`) — the only unguarded writer left; where the stale path *does* still exist, the machine resurrects a page the human removed. *Backlog for triage (unfiled): resolve the write target from disk with a re-create fallback, add content-hash drift to groom, add a Rebuild index button to Coop status.*
4. **`DESIGN.md`'s "the LLM writes only under nest/" is false as written, and unlike the vault Kip's raw layer is reachable by unsandboxed code — out-of-scope (with a doc-fix residue).** The violations are real and verified: the reminders skill rewrites `<coop>/reminders.json` wholesale (`skills/reminders/run.js:34` → `lib/reminders.js:32-34`); the docx/pptx skills write `<coop>/exports/` (`skills/docx/run.js:62,:101`; `skills/pptx/run.js:178`); `kip-control` writes `.henhouse/skills.json` and `llm.json` (`skills/kip-control/run.js:283-290`, `lib/llm.js:35-36`); and the tool writes *into* the "immutable" zone (`ensureInEggs` copies by basename, `hatch.js:67-70`; office conversion plants a derived `.md` sibling in `eggs/`, `office.js:268-277`). *Why it is out of scope anyway:* the vault's `1.Raw` immutability is likewise an instruction in a CLAUDE.md, not a filesystem ACL, and it only holds because Claude is the sole writer; Kip's equivalent instruction exists and the core workflows honour it — a full grep of `writeFileSync`/`copyFileSync`/`rmSync` in kip/scripts shows no write to `journals/`, `pages/`, or any pre-existing egg. Skills are arbitrary Node with the user's privileges, which `DESIGN.md:390-392` states plainly ("The runner limits blast radius but does not contain it") and §8 defers as sandboxing — re-litigating that here would add nothing. **The actionable residue is a one-line doc fix: reword constraint 2 to name the actual write set — filed as #118.**
5. **Append-only page history plus a real operation log is already stricter than the vault's Claude-owned wiki — low.** No code path deletes or rewrites nest prose: the complete nest write set is `pages.js:45,57`, `hatch.js:265` and `roost.js:256`, and updates are additive by construction. `clucks/` is append-only and gives Kip an audit trail the vault pattern has no equivalent for; `.roost/` segregation plus `rebuild-roost` gives the derived layer a destroy-and-rebuild story. The two deliberate divergences are documented and defensible: the whiteboard source page is a full replace because the board is the real raw (`hatch.js:216-226`, `DESIGN.md:227-230`), and `nest/index.md` is marked "Do not hand-edit" on the artifact itself (`roost.js:236-237`). The cost of this strictness is not immutability but synthesis — never rewriting prose is why reconciliation is deferred to a report-only groom — which is §6's problem, not this one. — **[already-covered · low]**

**Bottom line for this dimension.** Kip's coop model is *stronger* than the vault's on derived-state hygiene and auditability, and *weaker* on the two things the vault states as plain rules: raw immutability (asserted, never checked, and answered by re-deriving + duplicating) and single-owner wiki layers (Kip's is append-shared with a human the machine neither sees nor protects). Findings 1-2 are filed (#113, #115); finding 3's residue goes to triage; finding 4's residue is #118.

## 11. The mapping, assessed: hatch=Ingest, peck=Query, groom=Lint

Strength order: **groom=Lint > peck=Query > hatch=Ingest**.

- **groom=Lint is near-exact** — contradictions and orphan pages exist as code and are report-only by design, falling short only in that a changed raw file is indistinguishable from a brand-new one (lint-3) and that findings never leave the report (§9). One correction to the tidy 1:1: the vault's *third* named Lint check, un-ingested raw, does not map to groom at all — it lives in hatch's `collectPendingSources` (`hatch.js:318-385`); groom reads only `pages` + `pages_fts` (`groom.js:297-299`). Groom implements 2 of the vault's 3 named checks, plus 9 more.
- **peck=Query is mechanically right** (FTS over `meta.db` runs before any nest file is opened, `peck.js:399-400`) **but inverts the vault's spirit**: the querier reads raw bodies rather than a synthesis index — the per-page LLM summary the index already returns is dropped at `peck.js:122`, the sole reformulation pass is gated behind a threshold filler words defeat (`peck.js:152`), and outbound `[[links]]` are never followed. And peck is *also* an Ingest surface: the statement branch files unconditionally (`peck.js:403-411`) — `peck ↔ Query` describes half of peck.
- **hatch=Ingest is the weakest**, because the vault's Ingest is defined as "raw → synthesized page *traceable* to raw", and the default path delivers neither half: the drafted update body never sees the target page (`hatch.js:142-143`) and no provenance is written forward (`pages.js:56`). Hatch is also under-described by the mapping: it is Kip's only summary/index builder (`hatch.js:184`).
- **The obligation the mapping assigns to nobody: reconcile-at-write.** The vault requires the write itself to resolve — or at least name — a conflict with what the wiki already says. Kip splits that job across a hatch that appends blind, an answer prompt with no conflict rule, and a groom that is forbidden to write, so reconciliation is deferred to a report no stage is obligated to act on. #114 (existingContent into the default update) and #116 (compare/contrast rule in the answer prompt) are the two halves of giving it an owner.
